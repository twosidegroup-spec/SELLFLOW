# Deployment

Build targets and how the APK reaches a seller.

SellFlow is distributed **through its own website, not Google Play.** No
Play-specific dependency has been added and none is needed: the APK is an ordinary
production Android application. Play-specific obligations only become relevant if a
Play submission is ever chosen, and they are recorded in
`docs/google-play-sms-policy.md` rather than implemented.

## Prerequisites

Nothing is checked in. `android/` is generated by Continuous Native Generation and
is git-ignored. Never edit it by hand.

- **Node** 22.13.0
- **JDK 17**
- **Android SDK** with platform 36 and build-tools
- `ANDROID_HOME` set, and the SDK's `platform-tools` on `PATH` for `adb`
- For a cloud build instead: `eas-cli` and an EAS account that owns the project

## Native configuration this phase adds

One thing, and it is the only thing:

| File | Change |
| --- | --- |
| `app.json` | `plugins` gains `./plugins/withSellflowSms` |
| `plugins/withSellflowSms.js` | Adds `RECEIVE_SMS` and the `SMS_RECEIVED` receiver to the generated manifest. Idempotent. |
| `modules/sellflow-sms/` | The local Expo module (Kotlin provider parsers, receiver, candidate queue, JS bridge) |

No autolinking key is needed: `./modules` at the app root is where
`expo-modules-autolinking` looks by default. (`expo.autolinking` is not in the
SDK 57 app-config schema, so adding it would fail `expo-doctor`.)

`ios/` is untouched. The module declares `platforms: ["android"]`, so nothing is
added to the iOS project and the iOS build is unaffected.

The permission is deliberately **not** in `app.json`. It reaches the manifest
through the plugin so the entire native SMS surface is one reviewable file with a
comment on every line — see `docs/google-play-sms-policy.md`.

## Regenerating the native project

```bash
npx expo prebuild --platform android --clean
```

Verify the manifest came out right:

```bash
grep -c "uses-permission android:name=\"android.permission.RECEIVE_SMS\"" android/app/src/main/AndroidManifest.xml   # 1
grep -c "<receiver" android/app/src/main/AndroidManifest.xml                                                         # 1
grep -c "<application" android/app/src/main/AndroidManifest.xml                                                      # 1
npx expo-modules-autolinking resolve --platform android --json | grep SellflowSmsModule
```

The `<application>` count matters: a manifest with two is invalid and Android
ignores the receiver without an error anywhere. That failure mode is real — it
happened during development, and `withSellflowSms.js` now writes `<application>`
back as an array for exactly that reason.

Running prebuild a second time over an existing `android/` must leave the counts at
1. The plugin is idempotent; that is worth checking after any plugin change.

## Development build

```bash
npm ci
npx expo prebuild --platform android
npx expo run:android                    # build, install and launch on a connected device
```

With a device over adb:

```bash
adb devices
adb install -r android/app/build/outputs/apk/debug/app-debug.apk
```

The Metro server runs separately:

```bash
npm start        # expo start --dev-client
```

The **Parser check** panel on *Payments → Automatic detection* exists only in a
development build (`__DEV__`). It is how a real provider message gets used to
confirm or extend a parser — see `modules/sellflow-sms/fixtures/README.md`.

## Cloud build (EAS)

```bash
npm run eas:verify                    # resolves eas.json profiles offline, no account needed
eas build --profile development --platform android     # APK, internal distribution
eas build --profile preview    --platform android     # APK, EXPO_PUBLIC_SOFTWARE_CHANNEL=preview
eas build --profile production --platform android     # AAB
```

Profiles already exist in `eas.json`:

| Profile | Type | Signing | Use |
| --- | --- | --- | --- |
| `development` | APK | debug | Device QA. Has the dev client and the parser-check panel. |
| `preview` | APK | release | What sellers install from the website. |
| `production` | AAB | release | Only if Play submission is ever chosen. |

`preview` is the distribution profile. Direct APK distribution needs no
Play-specific configuration, no AAB, and no special entitlement.

## Signing

Release signing is an EAS-managed keystore. No `.jks`, `.p8` or `.p12` is in the
repository, and `.gitignore` blocks them if one ever lands there.

Credentials must never reach a commit:

```bash
eas secret:list
grep -r "service_role\|BEGIN PRIVATE KEY\|eyJhbGciOi" src/ modules/ app.json eas.json
```

The app ships only the **public anon key**. Money writes go through
`SECURITY DEFINER` functions that re-authorise against the session, so the anon key
cannot move money by itself — see migration `0024_payment_grants.sql`.

## Publishing the APK

```bash
eas build --profile preview --platform android
```

Upload the resulting APK to the website's download path, alongside the SHA-256 so a
seller can verify what they downloaded:

```bash
sha256sum app-release.apk
```

Nothing about the APK depends on Play. It is a standard signed Android package,
installable from a browser download, and Android's own permission model applies in
full: the seller sees a real permission dialog, and can decline it and keep using
the app.

## Before shipping an SMS build

`docs/device-qa-checklist.md` is the gate. In short:

- [ ] A development build installs and the receiver fires
- [ ] Permission is requested, explained, granted and revocable
- [ ] A **real** payment notification is received, parsed, ingested, matched and settled
- [ ] A duplicate message does not pay twice
- [ ] Wrong amount, wrong account and no-payer cases land in review, not settlement
- [ ] Offline queue and retry, and app restart, lose nothing
- [ ] `adb logcat` shows no message text
- [ ] Each provider parser has been checked against a **real captured** message

That last one is currently **not done for any provider.** See the verification
section of `docs/native-sms-architecture.md`.
